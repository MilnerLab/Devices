# ESP301 Serial Interface — Maintainer Guide

Reference for anyone maintaining the ESP301 driver
(`control_readout/esp_301/controller.py`). Scope is the **driver and its serial/USB
transport** only. For how the XCORR application drives this axis stack, its scan-side
failure handling, and the auto-recovery watchdog, see the XCORR program maintainer doc
(`App_Apps` — `app_apps/routines/xcorr/XCORR_MOTION_CONTROL.md`).

---

## 1. Transport & hardware facts

The Newport ESP301 speaks a simple ASCII command protocol. Two transports, and they differ
in one way that bites people:

| Transport | Path | Baud |
|---|---|---|
| **USB** (this rig) | ESP301 → **TI 3410 USB bridge** → virtual COM port (**COM7**) | **921600, fixed** |
| RS-232 | direct serial | front-panel setting, typically 19200 |

- **The USB baud is 921600 and is *not* the front-panel baud setting.** Setting the front
  panel to 19200 does not change the USB rate. Pass `baud=19200` only for the RS-232 path.
- **Windows device:** InstanceId `USB\VID_104D&PID_3001\0000000000000000`. On a fresh
  machine the TI-3410 virtual-COM driver may need to be bound manually (Windows does not
  always auto-bind it) — see the deployment/connection notes.
- **Axis map (hard-wired, verified correct):** axis 1 = **FMS300PP**, axis 2 = **MFA-CC**,
  axis 3 = **UTS150CC**. The 1-based axis number *is* the device `address`.

### The single most important invariant

**The controller CPU / front panel is independent of the USB serial channel.**

- A working front panel and stages that jog by hand **do not** prove the serial link is
  healthy.
- Conversely, a silent serial link **does not** mean the controller is dead.

Every misdiagnosis in this subsystem's history (see §9) came from conflating the two. Always
cross-check the front panel against the serial link before concluding anything.

## 2. Protocol & driver structure

**Wire format:** `<axis><cmd>\r`; replies are read with `readline()`. Examples: `1PA10.0`
(move axis 1 to 10 mm), `1TP` (position), `1MD?` (motion done → `1`/`0`).

| Command | Meaning |
|---|---|
| `MO` / `MF` | motor on / off |
| `OR[mode]` | home / origin search |
| `PA<x>` / `PR<d>` | absolute / relative move |
| `TP` | tell position |
| `MD?` | motion done? (`1` = done) |
| `VA<v>` | set velocity |
| `ST` | stop with deceleration |
| `TE?` | top of error buffer (`0` = no error) |
| `VE?` | firmware version (good liveness probe) |

**Classes** (`control_readout/base/controller.py`, `.../esp_301/controller.py`):

- `Controller` (base) — owns one connection + a device registry + an `RLock`
  (`_lock`) that serializes all hardware access.
- `ESP301Controller` — implements the transport (`_open`/`_close`) and the addressed
  motion primitives. **Both IO paths resync before writing:** `_write(cmd)` does
  **`reset_input_buffer()` → write** (write-only commands — `MO`/`MF`/`OR`/`PA`/`PR`/
  `VA`/`ST` — which get no reply); `_query(cmd)` does **`reset_input_buffer()` → write →
  `readline()`**; both under `_lock`. **Invariant:** every byte to/from the port goes
  through one of these two — a naked `serial.write()` anywhere else reopens the FM-2
  trigger (see §3).
- `Device` — a single axis; drives hardware only through the controller's primitives.

**Motion model:** `move_absolute`/`move_relative`/`home` send the command, then call
`wait_for_motion`, which — after an ~80 ms settle — polls `MD?` at **10 Hz** until done, and
**fails fast** on a comms fault (see FM-3).

## 3. Failure modes

Each is tagged with its resolution status. **Confirm the front-panel invariant (§1) first.**

### FM-1 — Framing desync  ·  **RESOLVED** (resync fix)

- **Symptom:** a move never completes; after the full 120 s it raises
  `Timed out waiting for axis N` — almost always axis 1. Front panel + manual motion fine.
- **Root cause:** under fast (20 Hz) `MD?` polling, one late or dropped reply desyncs the
  strictly-paired write/`readline()` stream **off-by-one for the rest of the session**.
  `MD?` then keeps reading the *previous* command's stale reply, which never starts with
  `1`, so `motion_done` is `False` forever. It looked axis-1-specific only because axis 1 is
  polled first. Compounded by G20 (see FM-3): `''.startswith("1")` is `False`, so a timed-out
  read was indistinguishable from "still moving".
- **Confirm:** exactly one ~120 s "axis N stuck" error; front panel healthy.
- **Fix:** `_query` now `reset_input_buffer()`s before every write (a late prior reply can
  never be read as this command's), the poll dropped to 10 Hz, and a settle was added before
  the first `MD?`. Regression test: `test_esp301_resync.py` (4/4; the three resync cases
  were 1/3 on the pre-fix code — they reproduce the bug offline against a fake serial. The
  4th case, `test_write_flood_drains_on_every_write`, guards the FM-2 `_write` drain).

### FM-2 — USB-bridge wedge  ·  **TRIGGER IDENTIFIED** (prevented by the resync fix; recovery = re-enumerate)

- **Symptom:** **every** command on **every** axis returns `b''` (the bridge sends zero
  bytes). The port still *opens* cleanly; the front panel + manual motion still work.
- **Distinguish from FM-1:** FM-1 is one axis with a desynced (but live) stream; FM-2 is
  **total silence on all axes**, reproducible even with raw `pyserial` on a fresh open with
  no `reset_input_buffer`. FM-2 is a transport wedge, not a protocol desync — once wedged,
  the resync fix **cannot** clear it (only re-enumeration does).
- **Root cause / trigger (identified):** the host **writing without draining replies**
  degrades and then wedges the TI-3410 bridge (endpoint FIFO / firmware) while the ESP301
  CPU stays alive. The old 20 Hz no-resync driver produced this via *desync* — it kept
  writing `MD?` while reading stale/empty, i.e. never truly draining the current reply — and
  the damage accumulated across reconnects until the bridge collapsed. The
  read-every-reply pattern the resync fix enforces does **not** wedge it.
- **Trigger analysis** (test-to-failure, `XCORR_WEDGE_TESTING_20260721.md`):
  - **CLEARED — H1:** idle queries at ~79 Hz, reading every reply — survived.
  - **CLEARED — H2:** `reset_input_buffer()` before every write at idle (~21 Hz) — survived.
  - **CONFIRMED — H3:** writing **without draining** replies (~23k cmds/s saturating the
    921600 wire, zero reads) wedges the bridge in < 60 s. **This is the trigger.**
  - **CLEARED — H4:** 10 Hz `MD?` polling through real moves up to **70 s / ~500 continuous
    polls** (well past the ~27 s of the 00:11 event), reading every reply — 0 empties. The
    "fast polling through a long move" theory is **falsified**; poll rate is not the axis of
    failure, draining every reply is.
  - Interpretation of 00:11 (wedged *with* the fix loaded): it was the *first reconnect*
    after a day of the old desyncing driver, so the bridge was already degraded (H3-style)
    and never re-enumerated — the fix read true replies but can't revive an
    already-wedged bridge.
- **Prevention:** the resync fix itself (one-write-one-**read**, `reset_input_buffer()`,
  10 Hz poll), **plus** the `_write` hardening (2026-07-21): the write-only path now also
  `reset_input_buffer()`s before every write, symmetric with `_query`. Originally only
  `_query` drained; a burst of write-only commands (`MO`×3 at bring-up, velocity setup, a
  stop broadcast) was fire-and-forget — a small bounded instance of the H3 not-draining
  trigger — and is now closed. **Never let the driver write without draining first.** See §5.
- **Confirm:** raw check returns `b''` on `1TP` for all axes **and** the front panel works.
- **Recovery:** §4 (re-enumerate once). Axis positions survive a bare re-enum; a full power
  cycle resets them (not homed, motors off).
- **Soak-verified:** 15 min continuous grating sweeps, 6,276 polls @ 10 Hz, 0 empties —
  no cumulative degradation. The prevention holds for sustained/unattended operation.

### FM-3 — Comms-fault misreported as a stuck axis (G20)  ·  **RESOLVED**

- Previously a silent link read as a stuck stage and hung the full 120 s. Now `motion_done`
  **raises** on an empty read, and `wait_for_motion` retries a small bounded number of times
  (default 3) then fails **fast** (seconds) with the `TE?` code and the message
  *"communication fault, not a stuck stage … Check the COM7 link, not the mechanics."*
- **Maintainer note:** that message means **check the link (FM-1/FM-2), not the mechanics.**
  It is the app-level hook the auto-recovery watchdog catches.

## 4. Diagnosis & recovery

### Raw link check (the ground-truth probe)

Bypass the whole stack — open the port directly and ask for a position:

```python
import serial, time
ser = serial.Serial("COM7", 921600, timeout=0.5)
ser.reset_input_buffer(); ser.write(b"1TP\r"); time.sleep(0.15)
print(ser.read(ser.in_waiting or 1))   # b'0.00000\r\n' = healthy; b'' = wedged (FM-2)
ser.close()
```

- Number back → link healthy.
- `b''` on all axes **+ front panel works** → FM-2 wedge.
- One-axis ~120 s "stuck" → FM-1 (should not occur post-fix; if it does, the fix regressed).

### Recovery — force USB re-enumeration (clears FM-2)

Any one of these; all require the physical device or admin rights:

1. **Physically replug** the ESP301 USB cable, or power-cycle the controller.
2. **Elevated PowerShell** (this Windows build supports `/restart-device`):
   ```powershell
   pnputil /restart-device "USB\VID_104D&PID_3001\0000000000000000"
   ```
3. Elevated `Disable-PnpDevice` / `Enable-PnpDevice` on the same InstanceId.

Non-elevated PnP attempts fail with *"Generic failure"*. Verify recovery with the raw check.

> **The CPU keeps axis positions across a bridge re-enum** (the front panel never lost
> power). After recovery, reopen the port and resume — **no re-home is needed.** This is what
> makes unattended auto-recovery viable (see the XCORR program doc).

## 5. Prevention guidance

Best practice for driving this bridge safely (validated by the H1–H4 test-to-failure and
the `_write` write-flood regression guard):

1. **Never let writes accumulate undrained; drain on every command.** This is the
   load-bearing rule — H3 shows writing without draining is what wedges the bridge (FM-2),
   and H4 shows that *with* every reply drained even 70 s of continuous 10 Hz polling is
   fine. `_query`'s one-write-one-`readline()` enforces it on the read path; `_write`'s
   pre-write `reset_input_buffer()` enforces it on the write-only path (which has no reply
   to read). Between them, no code path can outpace the drain.
2. **Poll `MD?` at ≤ ~10 Hz.** 20 Hz was above the ASCII parser's safe ceiling behind the
   TI-3410 and provoked the FM-1 desync (which then degrades into an FM-2 wedge).
3. **Keep the `reset_input_buffer()` per query** — it cures FM-1 and is safe (H1/H2).
4. **Settle after a move command** before the first `MD?` so the first poll can't collide
   with the controller still parsing the move.

Verified by a 15 min continuous soak (6,276 polls, 0 empties) — no cumulative wedge.
